# Backend Batch Benchmarking (resbench_batch.py)

Run batch benchmarks using only the **engine backend** API; no frontend needs to be started.
Script: `scripts/resbench_batch.py`; example configuration: this directory.

## 1. What it does

One invocation = one batch: the **Cartesian product** of `databases × workloads × orchestrations`, all executed **serially**.

| Step | API called |
|---|---|
| Apply database parameters (optional; corresponds to the frontend "Apply Config") | `POST /web/bench/db/params` |
| Submit one test round | `POST /web/bench/startByForm` |
| Poll until completion | `GET /web/bench/status?historyName=<runId>` |
| Fetch this round's metrics and artifact completeness | `GET /web/bench/history/query?keyword=<runId>` |
| Tag / add a note (so the frontend history page can also find it) | `POST /web/bench/history/label` |

`startByForm` is the **engine's own API** (`BenchmarkController`); the frontend is merely one of its callers.
The script calls the engine directly, loading no frontend code and depending on no frontend build or runtime. The advantage of going through this API is that
**the connection information, fault injection commands, and schedule XML are all generated by the backend**, so the script does not need to hand-write those XML files;
the backend also writes `run-meta.json`, which is why the frontend history page can find this batch of results by tag/orchestration.

Once running, Ctrl+C (or `kill`) is **safe**: the script stops **the round it just submitted itself** and then exits,
rather than leaving a child JVM running on the engine for hours and holding the "only one job accepted at a time" gate. If the job on the engine belongs to someone else,
the script recognizes that and will not touch it. See the end of Section 5 for details.

## 2. Parameter conventions: identical to the frontend, plus one extra field

The fields the script sends to the engine correspond one-to-one to the frontend's three panels: "Database Config / Workload / Fault Injection".

- `autoTimingMode` is hard-coded to `fixed-time`, and `runOptions.monitorIntervalSec=1/create/load/execute` are hard-coded to `true`
  — this is exactly how the frontend's `buildRequestBody()` hard-codes them;
- It does not send `dbKey / orchestrationId / source / envInfo`, nor `delaySeconds`
  — these do not exist in the frontend form;
- The run name (`historyName`) is generated by the engine as `<workload name>_<testName>_<timestamp>`; the script does not assemble it itself.

The script has **one more field** than the frontend form: **`testName`** — it is a field of `StartByFormRequest`,
and the frontend history page treats it as the "test name", but the frontend benchmark form does not fill it in. The script supplies the composite name
`<db key>__<workload key>__<orchestration key>`, so both the archive directory `results/<run name>/` and
the XML file names in `config/generated/` carry the experimental environment information.
It **does not change engine behavior** (it only affects naming, and the engine forcibly retains the workload name prefix).

`containerName` (the **container name** input box in the frontend's "Database Config"; `databases[].container` in the script)
is also a **top-level field** (sibling to `faults`, not inside `database`). When non-empty, the engine wraps chaosblade-type faults
in `docker exec <container> …` and injects them inside the container — see §3.1 and `docs/batch-script-usage.md`.
If left empty (the frontend leaves it blank / the script does not write `container`), this key is not sent at all, and behavior is byte-for-byte identical to before.

`key` fields such as `dbKey` exist only in the YAML; they are names the script uses internally to refer to one another and are **never sent to the backend**.

## 3. The three configuration files

### 3.1 `databases.yaml` — a single file may contain multiple databases

```yaml
databases:
  - key: og-local            # internal reference name for the script + part of the result directory name; not sent to the backend
    dbType: opengauss        # opengauss | mysql | postgresql | oceanbase | gaussdb
    deploymentType: standalone
    standalone: { ip: YOUR_DB_HOST, port: "5434", username: YOUR_USER, password: <password> }
    container: og-db         # optional: fill in the container name when the database runs in a Docker container (see the end of §3.1)
    # optional: corresponds to the frontend "Apply Config" button
    dbParams:
      bufferPool: 2GB
      maxConnections: "500"
      restartCommand: "nohup gs_ctl restart -D /gaussdb/data >/tmp/x.log 2>&1 &"
```

- Only the connection information that will **actually be used** is validated: standalone does not look at `distributed`, and distributed does not look at `standalone`.
- The rules for `dbParams` are the same as the frontend: only standalone `opengauss/postgresql/mysql` can be changed;
  for og/pg these two parameters take effect only after a restart, so `restartCommand` is required.
  How to write the command, and how to investigate a "read-back mismatch", are covered at the end of this section.
- `dbParams` is applied **once before this database's first round**, and all later rounds reuse it (avoiding a database restart every round);
  the applied result is recorded in the `database.params` archive under the real parameter names (`shared_buffers` / `max_connections`).

**`container` (the database runs in a Docker container)** — if a container name is provided, chaosblade-type faults for that database are wrapped in
`docker exec <container> …` and executed **inside the container**; all three commands — inject, recover, and self-check — are wrapped together:

- It applies only to chaosblade-type faults (`cpu` / `memory` / `disk` / `file` / `process`).
  DBChaos faults in the catalog (`connection.*` / `transaction.*` …) go over JDBC and **never enter the container**.
- **Network-type faults (`faultinject.fault.network.*`) are the exception and still target the host NIC**
  (the container NIC name differs from the host's, and network namespaces are isolated); the engine logs a WARN. This is intentional.
- Paths for disk-type faults (`path` / `src-path` / `file-path` / `filepath`) are resolved as **in-container** paths
  — use the in-container path read via `SHOW data_directory`, not the host mount path.
- Prerequisites: chaosblade is installed in the container (`/opt/chaosblade/blade`), the agent's OS user is in the docker group,
  and the container name resolves on the agent host. A wrong container name will not produce a 4xx; it will show up as a `docker exec` failure on the agent side.
- The container name is recorded in `run-meta.json` as `database.containerName`, and there is also a column in the CSV, so you can tell after the fact where the fault was injected.

**For a containerized database, the "Apply Config" restart command must be written in docker form yourself** (the backend will not synthesize systemd/docker/gs_ctl for you):

```yaml
    container: pg-docker
    dbParams:
      bufferPool: 2GB
      maxConnections: "500"
      # The command is executed by the agent on the host and is **not** wrapped in docker exec, so use docker restart directly;
      # su - <user> -c merely borrows that user's docker group privileges (not needed if the agent is already in the docker group)
      restartCommand: "su - YOUR_USER -c \"docker restart pg-docker\""
```

There are trade-offs in how to write it, and the reasons are all in the engine implementation:

- **Foreground (without `&`)**: by the time `docker restart` returns, the container is already up, so the engine's subsequent "reconnected successfully" is meaningful.
  The cost is that the command must be fast — the agent's limit for a single command is 30 seconds; if the container shuts down slowly, reduce the shutdown time first.
- **Detached (`nohup … &`)**: it will not hit the 30-second limit, but the engine connects immediately **after the command returns**,
  when the database is very likely not yet down, so both "reconnected successfully" and `restarted=true` will be false. With detached mode you must
  verify on the database yourself with `SELECT pg_postmaster_start_time();`.
- **Do not redirect output**: the agent's stdout/stderr is collected by the engine into `restartOutput` (visible in the frontend);
  `> /tmp/x.log 2>&1` amounts to hiding the only error message in a file on the database host.

**Parameters were written and the database was restarted, yet the read-back still shows the old values** — the most common cause is that **the container was started with command-line parameters**
(such as `-c shared_buffers=12GB` in the image CMD): command-line parameters take precedence **over** `postgresql.auto.conf` written by
`ALTER SYSTEM`, so the only fix is to change the container startup parameters; no change to `dbParams` can override them.
When application fails, the script lays out the evidence (`restarted` / `waitedSec` / the restart command sent / exactly which two items differ)
and does not block the benchmark; `waitedSec` is not a criterion (the engine starts connecting only after the command returns).

### 3.2 `workloads.yaml` — a single file may contain multiple workloads

```yaml
workloads:
  - key: sm-600
    name: smallbank          # smallbank | tpcc (the engine accepts only these two)
    params:
      accountsNum: "1000"
      terminals: "20"
      duration: "600"        # optional: takes effect only for rounds without faults, see §4
      amalgamateWeight: "15"
      balanceWeight: "15"
      depositCheckingWeight: "15"
      sendPaymentWeight: "25"
      transactSavingsWeight: "15"
      writeCheckWeight: "15"
```

tpcc's `params` are `warehouses / concurrency / duration / reload`.
`reload: true` means create tables + load data. Building warehouses is expensive (in this environment, 1000 warehouses measured at **4h08m**), and the engine decides whether to build warehouses
based only on `runOptions.reload` and **never asks how many warehouses the database already has** — so before the
**first round of each (database + this workload)**, the script first checks the actual warehouse count in the database (`POST /web/bench/tpcc/warehouse/verify`):

| What was found | What the script does |
|---|---|
| Warehouse count = configuration | Run it directly as a normal test, without building warehouses; later rounds do not need to build either — saving this warehouse build |
| Warehouse count ≠ configuration (not built / too many / too few) | **First run the warehouse build as a separate round** (warm-up round: no faults, `reload=true`), **wait for it to finish**, then run the formal rounds (the wait limit is set by `--build-timeout`); all subsequent rounds in this group use `reload=false` |
| Cannot be determined (cannot connect to the database / no permission / timeout / the engine is an old build) | **Do not guess**; execute according to the `reload` configured here |

Two things to note:

- The criterion **looks only at warehouse count, not district**. So "warehouse count matches, but district rows are insufficient" (a previous load was interrupted,
  data incomplete) counts as **passing** and is not rebuilt — the script prints a prominent `!` warning with the actual/expected district values,
  and this round's metrics should be read as "data may be incomplete".
- "Cannot be determined" is not the same as "warehouse count mismatch": the count is **unknown**, not **different**, so this does not trigger a multi-hour
  warehouse build out of nowhere; instead it falls back to the `reload` configuration. In the examples, tpcc always has `reload: true`, meaning that in this case
  **warehouses will still be built**, but the script will state explicitly "could not verify; executing per configuration".

Each (database + workload) is checked **only once, in the first round**; later rounds neither check again nor re-read the YAML.
OceanBase does not support tpcc, and the script reports an error at startup.

### 3.3 `orch/*.yaml` — a single file may hold **multiple** orchestrations

A single file can contain multiple orchestrations, each with its own `key` (used to distinguish each round's results):

```yaml
name: combo-demo                        # optional: the overall orchestration key for this file, used only to name the batch directory

orchestrations:
  - key: combo-A                        # the name of this orchestration, used in the result directory name
    batches:
      - duration: "60"                  # optional: uniformly override the duration of all faults in this batch to 60
        faults:
          - nameKey: faultinject.fault.connection.surge    # within the same batch → injected simultaneously
            params: { concurrent-connections: "200" }
          - nameKey: faultinject.fault.sql.plan_flip
            params: { threads: "16" }

      - at: 93                          # optional: the absolute injection time of this batch (seconds)
        faults:                         # once at is written, "previous batch end +30s" no longer applies
          - nameKey: faultinject.fault.transaction.massive.rollback
            params: { threads: "16", rollback-rate: "80" }

  - key: combo-B                        # the second orchestration to run next in the same invocation
    batches:
      - faults:
          - nameKey: faultinject.fault.cpu.load
            params: { duration: "30" }
```

The top level also supports two other forms with the same effect; **old files do not need to be changed**:

| Top-level form | Meaning |
|---|---|
| `orchestrations: [...]` | Multiple orchestrations in one file; **every entry must have a `key`** |
| `key:` + `batches:` | Single-orchestration file (the form above with only one entry) |
| A batch list written directly | Single-orchestration file; `key` is taken from the file name |

**The top-level `name:` (optional; can be added to all three forms)** is the overall orchestration key of this **file**, used only to name
the batch directory of this invocation (see §6): `batch-results/<timestamp>_<db key>_<workload key>_<name>/`.
If omitted, it falls back to the file name (`e1-orch.yaml` → `e1-orch`); when multiple orchestration files are passed in one invocation, they are joined with `+`
(`e1+combo-demo`). **It is distinct from each orchestration's own `key`, and the two do not affect each other**
— each round's result directory name and `--only-orchestration` still depend only on `key`.

- `key` must not repeat across **all files and all orchestrations in one invocation**
  — both the result directory name and `--only-orchestration` rely on it to distinguish.
- **Writing `batches:` as an empty list = this round injects no faults at all**, running only the workload.
  It can be used as a baseline/control group; note that in this case the workload duration is determined entirely by the `duration` written in `workloads.yaml`
  (there is no fault plan to back it up; see §4), so to be comparable with other rounds you must write it explicitly and long enough.
- **Faults in the same `faults:` list are injected simultaneously; different batches are serial.**
- **A batch can use `at: 93` to specify an absolute injection time (seconds, relative to the fault runner's start).** If written, it is used
  directly as the engine's `<planning>`, and the "first batch t=60s / +30s between batches" rule no longer applies; batches without `at` keep the original rule.
  Faults within the same batch still share one time. `at` must be written at the batch level, not inside an individual fault.
- To run faults one by one serially, put only one fault in each batch; to inject the same fault serially N times, write N batches.
- `nameKey` comes from the engine fault catalog: `curl -s http://127.0.0.1:8080/web/faults/catalog | jq '.[].nameKey'`
- Faults in the catalog (the 18 DBChaos ones) **can run without `duration`** — the catalog's `defaultDuration` is used;
  **OS-level chaosblade faults** (`cpu.load` / `network.package` / `disk.fill` / `process.*` …)
  are not in the catalog and **must have `params.duration` written explicitly**; otherwise the script reports an error immediately at startup and will not compute a duration from a guessed number.

## 4. Workload duration is computed automatically

Fault times are scheduled by the engine: **the first batch is at t=60s, and the next batch starts +30s after each batch ends**. The script applies the same rules in advance:

```
Batch 1 baseline b₁ = 60s
Batch i end eᵢ = bᵢ + max(duration of each fault in batch i)
Batch i+1 baseline bᵢ₊₁ = eᵢ + 30s
Plan end E = e_last batch
Workload duration = E + tail        (tail defaults to 20s, adjustable via --tail)
```

When a batch has `at:` written, that batch's `bᵢ = at` and is no longer derived from the previous batch; batches without `at` are still
appended after the **latest existing end point** according to the rules above. The plan end is `max(bᵢ + duration)` across all batches.

For rounds with faults, the workload duration is **computed entirely from the plan**: `plan end + tail` (tail defaults to 20s, adjustable via `--tail`).
The `duration` written in `workloads.yaml` does not participate — it used to be treated as a "lower bound" via `max()`, so after changing fault durations
the workload still followed the old plan length and the plan no longer matched reality. To lengthen the steady-state tail, adjust `--tail`.
`duration` takes effect only for orchestrations **without faults** (`batches: []`): the plan end for such a round is 60s,
so if it is not written the round will run for only 80s.
dry-run prints the time table for each batch and the final duration.

## 5. Running

```bash
# First view the plan (no jobs will be submitted)
python3 scripts/resbench_batch.py \
  --engine http://127.0.0.1:8080 \
  --databases scripts/batch-example/databases.yaml \
  --workloads scripts/batch-example/workloads.yaml \
  --orchestration scripts/batch-example/orch/combo-conn-planflip.yaml \
  --orchestration scripts/batch-example/orch/serial-os-faults.yaml

# After confirming, actually start the run
python3 scripts/resbench_batch.py ... --execute
```

Common parameters:

| Parameter | Default | Description |
|---|---|---|
| `--engine` | `http://127.0.0.1:8080` | Engine address; `envInfo` is not required |
| `--manager` | `http://127.0.0.1:8090` | res-manager address; during the benchmark it creates monitoring sessions, archives curves, and applies the curve criterion for "whether the fault took effect on the resource" (see §6) |
| `--no-monitor` | off | Do not create monitoring sessions or apply the curve criterion; run only the engine. When the manager or Prometheus is unavailable, it also automatically degrades to this mode without affecting the benchmark |
| `--monitor-metrics` | 10 default metrics | Metric IDs to collect, comma-separated. Defaults: `container.cpu.cores,container.cpu.usage,container.memory.usage,db.connections.usage,db.tps.agent,db.rollback.rate,host.netstat.retrans,host.netstat.reorder,host.disk.usage,host.process.stopped` |
| `--execute` | off | Without it, this is a dry-run that only prints the plan |
| `--out` | `batch-results/` | Result **root** directory: each invocation creates a batch directory under it, see §6 |
| `--tail` | `20` | How many seconds the workload runs after the fault plan ends |
| `--settle` | `15` | Seconds to wait after completion for the archive to land on disk before querying |
| `--cooldown` | `0` | Extra cooldown between rounds |
| `--end-margin` | `600` | If a round has not finished after "workload duration + this value", report a timeout (**normal** rounds) |
| `--build-timeout` | `21600` | Wait limit for the **warehouse-build warm-up round** (6 hours). 1000 warehouses measured at about 4h08m; increase it for more warehouses; on timeout it **stops the whole batch** and reports (it will not continue with "data may not be in place", nor leave a string of empty rounds blocked as "running") |
| `--busy-wait` | `600` | Maximum seconds to wait when a submission hits "running" (another job already exists on the engine). If the wait fails, it prints **the engine's own status** and cleanup instructions (see below), then **stops the whole batch** — continuing would only produce a string of empty rounds blocked by the same gate |
| `--keep-run-on-interrupt` | off | On Ctrl+C / `kill`, do **not** stop this round's benchmark job on the engine (by default it is stopped, see below) |
| `--only-db` / `--only-workload` / `--only-orchestration` | none | Subset filters for the Cartesian product (script run control, not sent to the backend); repeatable |

**On Ctrl+C / `kill` interruption**: by default the script stops **the round it just submitted itself** (`POST /web/bench/stop`,
body `[]`, the same path as the frontend "Stop" button), rather than leaving it running on the engine for hours. At the same time, this round is faithfully appended as a row
to the batch CSV (`note` states that it was interrupted and the archive is incomplete), the exit code is `130`, and the job is claimed by `startTimestamp` —
**if the job on the engine belongs to someone else, the script recognizes that and will not touch it** (this matters on a shared engine). There are three costs to be aware of:

- **Faults already injected are not automatically recovered**: OS-level chaosblade faults with a duration expire on their own, and DBChaos-type faults
  abort with the killed process; the full recovery command is in the archived `<workload>_<date>.config.xml` — use it to clean up.
- This round's archive is incomplete (no `metric.json`, etc.).
- `kill -9` / closing the terminal directly is not covered (the script has no chance to clean up); do it manually:
  `curl -X POST http://127.0.0.1:8080/web/bench/stop -H 'Content-Type: application/json' -d '[]'`

**The engine is stuck in "running" but there really is no job running?** That is debris left by a previous interruption: to admit a new job,
the engine looks only at the temporary state file `backend/resbenchmark/tmp/job.json` under the working directory; if it still says
`curState: RUNNING`, every status poll reinstalls this "lock". Change it to a terminal state to let new jobs through, **without restarting the engine**:

```bash
# First confirm what the engine itself says: startTimestamp is the previous start time; an empty message means it thinks it is still running
curl -s http://127.0.0.1:8080/web/bench/status

# Then look at that file (the engine re-reads it on every poll)
cat backend/resbenchmark/tmp/job.json
# {"curState":"RUNNING","startTimeStamp":"1790938926097","stopTimeStamp":"","success":false}
#        ↑ change it to "MANUAL" (or "GRACEFUL"), add a stopTimeStamp, keep success as false

curl -s http://127.0.0.1:8080/web/bench/status   # end should return to true
```

Note that `POST /web/bench/stop` **cannot clear it** (it only changes engine memory), and restarting the engine cannot clear it either (no reconciliation is done at startup).

## 6. Result recording

**One invocation = one batch directory**; all artifacts from this invocation land inside it, no longer flattened into `--out` and mixed with other batches:

```
batch-results/
└── 20261001_122713_pg-docker_tpcc-360_e1/          ← batch directory: <timestamp>_<db key>_<workload key>_<overall orchestration key>
    ├── runs-20261001_122713.csv                    ← one row per round, one file for the whole batch
    └── <db key>__<workload key>__<orchestration key>/
        └── <historyName>.json                      ← the full raw row of this round in the archive query
```

- The three keys in the directory name all come from the combination **actually to be run this time** (after `--only-*` filtering);
  with multiple databases/workloads/orchestration files they are joined with `+`, e.g.
  `20261001_122713_db-a+db-b_w1_e1+e2`;
- The overall orchestration key is the top-level `name:` of the orchestration file (see §3.3); if omitted, the file name is used;
- `runs-<batch timestamp>.csv` — contains `history_name` (the run name generated by the engine), database/workload/orchestration, `suite`,
  plan end, actual workload duration, success or not, elapsed time, whether artifacts are complete, and metrics
  (`stability` / `defence` / `recovery` / `rto` / `outage_seconds`), etc.;
- `<historyName>.json` — the full raw row of this round in the archive query. Repeated runs of the same combination accumulate in the same directory;
- `<historyName>.faults.json` — the injection/recovery result and self-check status of each fault in this round
  (the raw return of `GET /web/bench/inject/info`), used to answer "did the fault actually take effect";
- **`fault_inject`** column — `ok` / `failed:2/3` / `unknown` / empty (baseline rounds with `batches: []`).
  It answers **whether the fault actually took effect**: if the injection command fails, or the self-check is `NOT_ENFORCED`, it counts as `failed`.
  For `failed` rounds, the `defence` / `recovery` / `rto` on the same row **must not be read as "the database withstood this fault"**
  — the fault never landed, and the metrics are only baseline fluctuations of the workload. At the end, the script lists these rounds together;
- **`fault_inject_errors`** column — a compact detail of failed items (e.g. `Disk Fill(rc=1)`),
  empty when injection did not fail. It is `unknown` when no injection record can be found, or when the engine is an old build (no inject/info API);
- **`fault_verify`** column — a summary of self-check status (e.g. `ENFORCED:3` / `UNKNOWN:3`).
  `UNKNOWN` means the fault **has no self-check command configured** (this is the case for all OS-level chaosblade faults),
  so "effective or not" can only be judged from the `fault_inject` command return code, and the script does not treat it as a failure;
- `<historyName>.monitor.json` — the full curve criterion for this round: verdict, evidence, baseline/window intervals and
  deltas for each injection window, matched curve labels, and the complete archived curves;
- `json_file` in the CSV is a path **relative to the current directory**; `cat` it to view it, as before
  (except that there is now an extra batch directory level in front). If the whole batch directory is moved, this path becomes invalid; moving the whole `--out` together does not have this problem.

### 6.1 Monitoring curve criterion (the `monitor_*` three columns)

`fault_verify` only looks at the engine's self-check command; OS-level chaosblade faults (network, disk, process) have no self-check
and can only rely on the return code. **The three `monitor_*` columns fill exactly this gap**: from the curves archived by the manager,
they check whether the expected change appeared on the resource within the injection window. At benchmark start, the script creates a collection session
with `--monitor-metrics` (`queryStepSec=5`; the manager's lower bound has been relaxed from 10 seconds to 3 seconds, so archiving is at 5-second granularity, giving about 12 points for a 60-second injection window),
archives after normal completion/timeout, and then aligns windows as follows:

- For each injection batch, take `[injection start, injection end]`, and additionally the **30 seconds** before it as the baseline;
- Intervals are **half-open** `[lo, hi)`; the baseline does not include the sample point at the window start;
- The three batches (default t=60/150/240s) are judged separately; `ENFORCED` requires **all determinable windows to hit**.

| `monitor_verify` | Meaning |
|---|---|
| `ENFORCED` | In all determinable injection windows, the expected curve showed a change in the expected direction |
| `PARTIAL` | Some windows hit (e.g. collection broke during the 2nd injection) |
| `NOT_ENFORCED` | The curve has data, but there was no expected change in the injection window — **the fault most likely did not land** |
| `NO_DATA` | There is no curve in the archive, or no run start time, so windows cannot be aligned |

Criterion (`nameKey` suffix → curve / threshold; see `EFFECT_RULES` in the script):

| Fault | Curve | Hit condition |
|---|---|---|
| `cpu.load` | `container.cpu.cores` | Window mean at least 2 cores above baseline |
| `memory.load` | `container.memory.usage` | At least 5 percentage points higher |
| `connection.surge` | `db.connections.usage` | At least 5 percentage points higher |
| `transaction.massive.rollback` | `db.rollback.rate` | At least 1 tx/s higher; when this curve is absent, fall back to `db.tps.agent` rising at least 1.3× |
| `network.package` | `host.netstat.retrans` | At least 0.5 segs/s higher and at least 2× |
| `network.unorder` / `network.duplicate` | `host.netstat.reorder` | At least 0.2 events/s higher and at least 1.5× |
| `disk.fill` | `host.disk.usage` | Target mount point at least 3 percentage points higher |
| `process.stop` | `host.process.stopped` | A process in T state appears in the window and was absent from the baseline |

The `monitor_run` column records the monitoring pipeline itself: `archived` (the session ran to completion and was archived), `ok` (a session was created but did not reach archiving),
`failed` (the session could not be created), `disabled` (`--no-monitor`, manager or Prometheus unavailable), empty (old records).

`monitor_evidence` is compact evidence, in the form
`batch 1 network.package host.netstat.retrans=+3.20 hit; batch 2 … miss`;
window boundaries, curve labels, and raw data points are all in the `detail` / `series` of `<historyName>.monitor.json`.

**Note**: faults without a configured criterion (such as `filemove` / `fileremoved` / `filechmod`) do not participate in the statistics;
`ENFORCED` only means "all **determinable** faults left a trace on the curves", not "all faults took effect".

> The `host.disk.usage` / `host.netstat.retrans` / `host.netstat.reorder` /
> `host.process.stopped` / `db.rollback.rate` in the default metrics are newly added to the monitoring catalog. **The manager must have been restarted**
> for them to appear in `/monitoring/catalog`; without a restart, creating a session fails because of an "unknown metric",
> and that round's `monitor_run` is `failed`. `curl -s http://127.0.0.1:8090/monitoring/catalog`
> can confirm whether these 5 IDs are present.

Each CSV row is flushed + fsync'd as soon as it is written, so completed records are not lost even if the run is interrupted.
Each round also calls `history/label` to apply a `batch / <db key> / <workload key> / <orchestration key>` tag,
so the frontend history page can find this batch of results by these tags.

The segment in the combination directory name and in the engine run name (`<workload name>_<combination name>_<timestamp>`) **is the same string**,
so the archived directory under `results/` also shows at a glance what environment it ran on.
